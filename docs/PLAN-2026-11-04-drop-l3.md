## 一、为什么取消 L3

现状：应用内可以"只换内置 pi-web"（L3 热更新），清单放在固定 Release（F14）。但壳对 pi-web 有一串**隐含假设**：

- 启动参数 `node bin/pi-web.js --no-open -p <port> -H 127.0.0.1` 与 cwd
- run record 布局 `$AGENT/pi-web-run/<pid>.json`（附着/清孤儿）
- `/api/sessions` 的 `runningSessionIds`（退出确认 F22）
- `/api/sessions/<id>/export?inline=1` 返回 HTML（导出、冒烟 F18）
- 两个 build-time 补丁：折叠（chunk 锚点 + 改名）、导出（`if(1!==g)` 断言）
- 内置 Node 22.23.4 的下限
- `window.open` 新窗口路径（B1 修复）

任何一条被上游改动，L3 就可能把用户带进"能启动但某项功能坏"的状态（B2 就是例子）。要安全就得维护兼容门、安装后自检、`requiresShell`、回滚 —— 收益（省一次壳发版）远小于维护成本。

**结论：pi-web 版本与壳版本一对一固定，随 App 一起发布。** 上游有新 pi-web 时，发一版新 App（顺带带上壳侧修补）。

## 二、要删/改的东西

**代码**
- 删除 `src-tauri/src/hotupdate.rs`（L3 下载/切换/回滚/清单/进度）
- `sidecar::resolve` 去掉热更新 overlay 分支；启动时**清理已有 overlay**（把用户拉回内置固定版本）
- 删除 L1 的 npm 上游检查（`silent_check` / 提示文案 / 相关对话框）——已不能单独升，留着只会误导
- 菜单与托盘去掉「更新 pi-web…」
- 保留：应用更新（L2 + 正式/测试通道）、两个 build-time 补丁、窗口记忆、托盘、退出确认

**CI / 发布**
- `release.yml` 去掉「发布侧车清单到固定 Release `piweb-sidecar`」
- 应用 Release 不再附带 `piweb-app-*.tar.gz` / `piweb-sidecar.json`
- `make-dist.sh` 不再生成 L3 侧车包与清单
- 固定 Release `piweb-sidecar` 保留为历史资产（不再更新），下次可考虑删除

**版本规则**
- `sidecar.json` 仍是唯一版本源：pi-web / Node 版本固定在里面；**壳版本 = 这一对版本的标签**
- 每次发版必须：`npm run sidecar`（两个补丁必须打上）→ `npm run smoke`（导出真 HTML）→ `npm run smoke:app`（真启动 + 侧车端口可连）→ 本机验收 → 才发布

## 三、顺手升级 pi-web → 0.15.0

- 0.15.0 的 `engines.node` 仍是 `>=22.19.0`（内置 22.23.4 满足），pi SDK 仍是 1.5.0（与 0.14.2 相同）
- 所以升级面只在 pi-web 自身；两个补丁需要重新验证（上游若改了锚点，`npm run sidecar` 会直接失败）
- 与"取消 L3"一起放进 `0.3.2-beta.1`

## 四、运行期定期检查（新增）

现在只在启动时查一次，App 一直开着就永远不查。新增：

- 启动后 20s 照旧查一次（不变）
- 之后**每 6 小时**静默查一次（应用更新，按当前通道；沿用"同一版本只提醒一次"）
- 定时器是常驻线程，间隔可用 `PIWEB_PERIODIC_CHECK_SECS` 覆盖（测试用）
- 失败只写日志，不打扰

3. 真机：`0.15.0` 上导出 HTML 正常（B2 补丁仍有效）、自定义消息折叠仍生效
4. 定期检查：把 `PIWEB_PERIODIC_CHECK_SECS` 设成 30 秒，观察日志出现周期性检查记录
