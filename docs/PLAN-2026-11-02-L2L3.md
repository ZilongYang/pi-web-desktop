# L2 / L3 更新机制 —— 实施方案（2026-11-02）

> 状态：**已批准并实施**（子龙在对话中确认：L2 开源到 GitHub、签名不用 P3YTJX7552、签名仿效 zWGestures；L3 只下载 pi-web 并替换）。
> 本文件按批准时的方案存档；实施中的偏差与验证记录见文末「实施记录」。

## 0. 目标

让桌面版能跟上两类上游变化，而不必每月手动重建：

- **L2 应用自更新**：壳自身（含内置 pi-web / pi SDK / Node）有新版时，应用内提示 → 下载 → 替换 → 重启。
- **L3 侧车热更新**：只换 pi-web（不动 Node、不重装 app），用于跟 pi-web 的小步迭代。

## 1. 约束与取舍

| 决定 | 理由 |
|---|---|
| **开源到 GitHub（公开仓库 `ZilongYang/pi-web-desktop`）** | 用户指定；Release 同时充当 updater 与 L3 的发布源 |
| **发布产物用 ad-hoc 签名** | 仿效 zWGestures：下载者拿不到 Developer ID 公证，两者等价；ad-hoc 不依赖证书，任何机器可复现 |
| **本机日常构建用自签名固定证书** | 移植 zWGestures 的 `create-signing-cert.sh`：独立钥匙串 + key partition list，保持 designated requirement 稳定，免 TCC 重复授权与弹窗 |
| **不使用 P3YTJX7552（Chaoyang Xie 的 Developer ID）** | 用户明确要求；发布链路不依赖任何真实证书 |
| **dmg 用 `diskutil image create from`** | hdiutil 在 macOS 27 已废弃并实测失败（zWGestures 同结论） |
| **updater 密钥（minisign）独立于 Apple 签名** | Tauri updater 的完整性校验用私钥签名，公钥写进 tauri.conf；私钥只放 GitHub Secrets 与本地 `.secrets/`（gitignored） |
| **L3 只打包 `app/`（pi-web + 它的 node_modules），不含 Node** | 用户明确"只下载 pi-web 并替换"；Node 跟应用走（TLS 修复等由 L2 统一升） |
| **L3 安装到 `<app_local_data_dir>/sidecar/`，由 `sidecar::resolve` 优先使用** | 不改签名包内容；失败可回滚；app 升级后若包内版本更高，自动忽略旧 overlay |

## 2. L2 方案（应用自更新）

1. 依赖 `tauri-plugin-updater`；`tauri.conf.json`：
   - `plugins.updater.pubkey` = 本机生成的 minisign 公钥
   - `endpoints` = `https://github.com/ZilongYang/pi-web-desktop/releases/latest/download/latest.json`
2. 构建：`bundle.createUpdaterArtifacts = true` 仅在 CI/发布时通过 `--config` 打开（本地日常构建不需要密钥）。
3. 交互：
   - 启动后 20s 静默检查，24h 一次；有新版弹「下载并安装 / 稍后」
   - 菜单「检查更新…」= 先查应用（L2），无更新再查 pi-web（L3）
   - 安装 = 下载 → 安装 → `app.restart()`；进度写日志
4. CI（`.github/workflows/release.yml`，tag `v*` 触发）：macOS arm64 → 装侧车 → `cargo test` → `tauri build`（带签名密钥）→ `make-dist.sh` → 生成 `latest.json` → `gh release create`。

## 3. L3 方案（只换 pi-web）

发布侧（CI / `scripts/make-dist.sh`）：
- `piweb-app-<piWebVersion>-<target>.tar.gz`：`sidecar/app` + `manifest.json`（78MB 左右）
- `piweb-sidecar.json`：`{piWebVersion, nodeVersion, assets:{<target>:{url,sha256,bytes}}}`

客户端（`src-tauri/src/hotupdate.rs`）：
1. 取清单（curl；支持 `PIWEB_SIDECAR_MANIFEST_URL` 覆盖，便于本地演练）。
2. 与当前**生效**版本比较，只有严格更新才提示。
3. 确认后：下载 → 校验大小与 **SHA256** → 解压到 `sidecar-staging` → 校验目录结构。
4. 切换：`app/` 与 `manifest.json` **一起**备份到 `.prev/`，再换入新内容（版本号和内容必须一起换）。
5. 重启侧车：**强制自己起**（跳过附着），避免探活打到外部实例。
6. 成功判定：我们自己的进程在（`AppState.sidecar` 有值）+ 端口有 HTTP 应答；失败则回滚 `.prev`（含 manifest）再重启，失败原因写日志 + 弹窗。
7. 启动时 `recover_on_startup()`：上次切换崩在半路（`app/` 不完整）时用 `.prev/` 恢复。

## 4. 验证计划

- 单元：版本比较、文案分支（已有）。
- L3 端到端（本地 HTTP 假 Release）：
  - 正常升级：0.14.1 → 0.14.9，服务重启后 200，`.prev` 删除
  - 坏包回滚：0.14.9 → 0.14.10（删掉 `.next`）→ 自动回滚到 0.14.9，服务 200，提示"已回滚并恢复旧版本"
  - 外部实例干扰：本机 30141 跑着 0.14.1 时，升级后必须自己起在 30241，不能被"附着"误导
- L2：CI 出 `latest.json` + `.app.tar.gz.sig`；安装后版本号变化（首次发布后验证）。

**实施中修掉的 bug（4 个）**
1. `sidecar::resolve` 无脑优先 overlay → app 升级后被旧 overlay 顶住；改为"只在严格更新时生效"
2. 热更新探活只看端口 → 附着外部实例时误判成功；改为"自有进程 + 端口应答"双条件，并强制本次自起
3. 回滚只恢复 `app/` 不恢复 `manifest.json` → 版本号回来不了；改为两者一起备份/恢复
4. 重启时状态里残留 `Failed` → 回滚后被误判"旧版本也没起来"；重启时同步置回 `Starting`，快速失败判定加 2s 宽限

**环境问题（与代码无关）**
- 本机 `~/.cargo/config.toml` 走 tuna 的 **git** 索引，队列经常排到 100+，cargo 会长时间干等；改用 `--config source.crates-io.replace-with=rsproxy + sparse`（或 CI 上的默认 sparse）即可，几十秒完成。
- 我这边 shell 环境自带 `http_proxy/https_proxy=127.0.0.1:7890`，cargo 走代理拉国内镜像会卡死；构建时需 `env -u http_proxy -u https_proxy ...`。CI 不受影响。
