## 回归修复（2026-11-01 晚，用户实测反馈）

**症状**：把终端里的 `npx @agegr/pi-web` 结束掉 → 桌面版弹「pi-web 服务已停止响应」→ 点「重启服务」后应用自己起在 30241 并正常，但**那个弹窗每隔几十秒又出现一次**，一直刷。

**根因**（日志可复现，同一个时间戳附近有两行几乎相同的 `端口 30141 无应答`）：
1. 监控线程在启动时把端口**捕获进闭包**（附着模式下捕获的是外部实例的 30141）。
2. 点「重启服务」→ `restart_sidecar_now` 把全局标记复位 → 新起了一个盯 30241 的线程，**但旧线程没人停**，它继续每轮探测已经死掉的 30141 → 反复告警。
3. 告警没有去重，一次故障会每个周期弹一次。

**修复**：
- 监控改成**全局唯一**线程（`start_health_monitor` 只在 setup 调一次），每轮**重新读当前端口 + 当前模式**，而不是捕获；
- 一次故障只告警一次（`alerted` / `alerted_port`），探活恢复后才重新武装；
- `Mode::Starting`（重启中）和 `Mode::Failed` 期间跳过探测，杜绝"重启被误判成挂掉"；
- 文案区分场景：附着模式→「启动服务」（起自己的实例），自起模式→「重启服务」；
- 加测试开关：`PIWEB_HEALTH_INTERVAL_MS`（默认 10000）、`PIWEB_HEALTH_HEADLESS=1`（不弹窗、自动重启，用于自动化验证）。

**验证（headless，间隔 2s）**：
```
attached 30141 → 杀掉外部实例 → 无应答×3 → [failed]×1 → 自动起 30241 → ready 4.7s → 之后 40s 内无二次告警
计数：无应答行 3，failed 行 1，30241 监听正常
```

## 回归修复二（2026-11-01 夜，用户测试会话反馈）

**症状**：在桌面版的 pi 会话里，agent 报告 `mnemon` CLI `command not found`（`~/.mnemon` 数据在、但 CLI 不在 PATH）。

**根因**：`mnemon` 装在 nvm 的 node bin 里（`~/.nvm/versions/node/v24.14.0/bin/mnemon`），只有交互式 shell 的 `.zshrc` 才会把那个目录加进 PATH。而桌面版从 Finder 启动时继承的是 `/usr/bin:/bin:/usr/sbin:/sbin`，我之前手写的 PATH 白名单只补了 `.local/bin`、homebrew 等，**漏了所有版本管理器目录**。

顺带澄清：那条回复里"没有 mnemon_recall / mnemon_remember 工具"是另一回事——`~/.pi/agent/extensions/mnemon.ts` 这个 pi 扩展本来就只注入提示/guide/状态，不注册工具，与 PATH 无关。

**修复**（`src-tauri/src/sidecar.rs`）：
1. 侧车 PATH 现在 = 登录 shell PATH（缓存/后台探测）→ 常见目录兜底 → 继承值 → 包内 runtime（放最后，保证会话里的 `node` 和你终端一致）。
2. 兜底目录覆盖 nvm（按 `~/.nvm/alias/default` 优先，其余版本从新到旧）、volta/asdf/mise/fnm/nodenv、`Library/pnpm`、deno、go、conda、orbstack、x-cmd、mimocode/codebuddy/minimax/kimi/opencode/mavis、flutter、dotnet。
3. `zsh -lic` 探测后台跑（GUI 里实测 0.9–1.2s，偶发 >2s 卡住），成功写 `login-path.txt` 缓存（7 天）；启动不阻塞。
4. 日志打出 PATH 项数、来源、是否含 nvm/mnemon。

## 回归修复三（2026-11-02 凌晨，用户截图反馈）

**症状**：pi 界面顶部黄条「Plannotator: your Node v22.22.3 is missing the October 2026 TLS fixes (a compromised certificate authority); update to 22.23.4, 24.22.1 or 26.12.1 or later.」

**根因**：不是 pi-web 的 bug，也不是配置问题——桌面版的服务端跑的是**我内置的 Node**，pin 的是 `22.22.3`，正好在 2026-10 那批 TLS 修复（eMudhra CA 事件）之前一个版本。警告来自 `@plannotator/pi-extension` 的 `runtime-tls.ts`：它每次 Pi 启动检查一次 `process.version`，低于安全版本就打这条（每会话一次）。

**影响**：pi-web 进程的所有出站 HTTPS（模型 API、OAuth、更新检查）走的就是这个 Node 的 TLS 栈，缺修复意味着理论上可能被问题 CA 签发的证书 MITM。属于该升的告警，不是噪音。

**修复**：`sidecar.json` 的 `nodeVersion` 22.22.3 → **22.23.4**（Node 22 "Jod" 最新，2026-10-20 发布，官方 dist 校验通过）→ `npm run sidecar` → `npm run smoke`（通过：起服务 1.8s、API 正常、退出干净）→ `tauri build --bundles app`。

**验证**：包内 `Contents/Resources/pi-web/runtime/node --version` = `v22.23.4`；manifest `nodeVersionActual` = `v22.23.4`；运行中的侧车进程可执行文件正是这个路径；`http://127.0.0.1:30241/` 200。

## L2 / L3 更新机制（2026-11-02）

**L2 应用自更新（tauri-plugin-updater）**
- 生成 minisign 密钥（私钥只在 `.secrets/` 与 GitHub Secrets，公开仓库里只有公钥）
- `tauri.conf.json`：pubkey + `releases/latest/download/latest.json` endpoint
- 菜单「检查更新…」先查应用（有更新就「下载并安装」→ `app.restart()`），无更新再查 pi-web
- 启动 20s 后静默检查，24h 一次（注：0.2.7 起改为每次启动都检查）
- 实测：无 Release 时日志 `应用更新检查失败（Could not fetch a valid release JSON）`，不阻塞后续 pi-web 检查；有 Release 后的安装待首次发版验证

**L3 pi-web 热更新（只换 pi-web，Node 不动）**
- 清单 `piweb-sidecar.json` + 包 `piweb-app-<ver>-darwin-aarch64.tar.gz`（78MB）
- 流程：下载 → SHA256 校验 → 解压 staging → 结构校验 → `app/`+`manifest.json` 一起备份到 `.prev/` → 换入 → **强制自己起**侧车 → 双条件探活（自有进程 + 端口应答）→ 成功删备份 / 失败回滚
- 实测（本地 HTTP 假 Release + headless）：
  - 正常升级：0.14.1 → 0.14.9，切换后 30241 返回 200，`.prev` 自动删除
  - **外部实例干扰**：本机 30141 有 0.14.1 在跑时，升级后强制自己起在 30241（修掉了"探活打到外部实例上误判成功"的问题）
  - **坏包回滚**：0.14.10（删掉 `.next`）→ 提前判定失败（2s 宽限）→ 回滚到 0.14.9 → 服务恢复 200 → 提示"新版本启动失败，已回滚并恢复旧版本"
  - 回滚一开始只恢复了 `app/` 没恢复 `manifest.json`，导致版本号仍报新的；已修成两者一起换
- 陈旧 overlay：包内版本更高时自动忽略热更新目录（避免 app 升级后被旧 overlay 顶住降级）

**签名/打包（移植 zWGestures）**
- `scripts/create-signing-cert.sh`：本机固定自签名证书（独立钥匙串 + key partition list，免弹窗、TCC 授权稳定）
- `scripts/make-dist.sh`：发布产物 ad-hoc 签名；断言签名/架构/版本/无 get-task-allow/无构建者主目录/侧车可执行位；`diskutil image create from` 出 dmg；L3 包 + 清单 + SHA256SUMS
- 版本 0.2.0（壳）/ pi-web 0.14.1 / pi SDK 1.4.0 / Node 22.23.4
